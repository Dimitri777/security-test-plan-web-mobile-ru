# 1. Стратегия тестирования безопасности

## 1.1 Цель документа

Документ определяет высокоуровневый подход к тестированию безопасности платформы FinSecure (веб + мобильные клиенты). Отвечает на вопросы:

- Что будем тестировать?
- Зачем будем тестировать?
- Как будем тестировать?
- Кто будет выполнять тестирование?
- Когда тестирование будет проводиться в жизненном цикле проекта?

## 1.2 Цели

1. Выявить и подтвердить эффективность средств защиты финансовых данных клиентов и механизмов аутентификации.
2. Обнаружить уязвимости, которые могут привести к несанкционированному доступу, утечке данных или нарушению работы сервиса.
3. Проверить соответствие релевантным стандартам (OWASP ASVS, OWASP MASVS, принципы PCI-DSS).
4. Предоставить практические findings с чёткими оценками рисков и рекомендациями по устранению.
5. Создать повторяемый процесс тестирования безопасности, который можно интегрировать в CI/CD.

## 1.3 Область применения

### В области

| Компонент                 | Описание                                           |
|---------------------------|----------------------------------------------------|
| Веб-приложение            | Публичный и аутентифицированный UI (SPA + SSR)     |
| Мобильные приложения      | Нативные клиенты iOS и Android                     |
| Backend API               | REST и GraphQL endpoints                           |
| Аутентификация            | Вход, MFA, управление сессиями, сброс пароля       |
| Авторизация               | Ролевая модель (клиент, поддержка, администратор)  |
| Защита данных             | Шифрование в транзите и на хранении, обработка ПДн |
| Бизнес-логика             | Переводы, платежи, лимиты                          |
| Инфраструктура (ограниченно) | Открытые сервисы, заголовки, конфигурация TLS   |

### Вне области

- Физическая безопасность дата-центров
- Социальная инженерия сотрудников
- Полный анализ исходного кода сторонних библиотек (кроме критичных)
- Полноценный red-team / физическое проникновение
- Нагрузочное тестирование (кроме сценариев DoS)

## 1.4 Подход к тестированию

Используется **риск-ориентированный гибридный** подход, сочетающий:

1. **Автоматизированное сканирование** (SAST, DAST, SCA, статический/динамический анализ мобильных приложений)
2. **Ручное пентестирование** (бизнес-логика, сложная авторизация, мобильные особенности)
3. **Анализ конфигурации** (заголовки, TLS, разрешения мобильных приложений, certificate pinning)
4. **Моделирование угроз** (STRIDE / attack trees) в начале работ

### Уровни тестирования

| Уровень                    | Частота                        | Глубина                     |
|----------------------------|--------------------------------|-----------------------------|
| Непрерывный (CI)           | Каждый pull request            | Только автоматизация        |
| Спринт / Релиз             | Каждый крупный релиз           | Автоматика + точечное ручное|
| Полная оценка безопасности | Ежеквартально / перед релизами | Полное ручное + автоматика  |

## 1.5 Методологические основы

- OWASP Testing Guide v4.2
- OWASP Application Security Verification Standard (ASVS)
- OWASP Mobile Application Security Verification Standard (MASVS)
- OWASP API Security Top 10
- NIST SP 800-115
- PTES

## 1.6 Роли и ответственность

| Роль                       | Ответственность                                      |
|----------------------------|------------------------------------------------------|
| Руководитель тестирования  | Координация, отчётность, приоритизация рисков        |
| Пентестер(ы)               | Ручное тестирование, эксплуатация, PoC               |
| Инженер автоматизации      | Интеграция в пайплайн, настройка инструментов        |
| Команда разработки         | Исправление, поддержка ретестирования                |
| Владелец продукта          | Принятие рисков                                      |

## 1.7 Критерии успеха

- Все Critical и High findings устранены или официально приняты с компенсирующими мерами.
- Medium findings имеют планы устранения с владельцами и сроками.
- Покрытие критичных attack surfaces ≥ 90 % (по ASVS/MASVS).
- Findings воспроизводимы и имеют доказательства.

## 1.8 Ограничения и допущения

- Тестирование проводится в выделенном staging-окружении, максимально близком к production.
- Production-данные не используются — только синтетические.
- Деструктивные тесты (DoS, порча данных) требуют письменного разрешения.
- Мобильные приложения тестируются на физических устройствах и эмуляторах/симуляторах.
